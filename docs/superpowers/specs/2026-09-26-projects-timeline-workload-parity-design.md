# Projects Timeline and Workload Mockup Parity — Design

## Goal and boundaries

Bring the existing Projects Timeline and Workload views in `v6-port` closer to the supplied `iPop App v6.dc.html` mockup in layout, status colours, task/member interactions, and accurate counts. Use live project data, not the mockup's sample tasks, members, fixed date (`2026-09-23`), or frozen timeline origin (`2026-09-08`). Keep the current Weekly/Monthly/Yearly scale setting: it is a real user preference, not an extra to discard for screenshot fidelity. Do not change other modules, seed the development database, or introduce a database migration.

The existing project toolbar and project navigation remain in place. Work must preserve the substantial uncommitted changes in the `v6-port` worktree, especially in `Projects.razor`, `ProjectUiHelpers.cs`, DTOs, `ProjectService.cs`, `css/v6/projects.css`, and `index.html`; inspect current diffs immediately before editing and use scoped changes rather than whole-file replacement.

## Timeline view

Replace the present weekly buckets and compact milestone pills with a white card: a header with a human-readable date range plus previous / Today / next controls; a fixed task-name column; date columns and faint vertical rules; one task per row with status dot, ellipsized name, assignee line, and a horizontally positioned status-coloured bar; a red current-day line where today falls inside the range; and a footer legend for Today, To Do (grey), In Progress (blue), Review (orange), Done (green). Completed task names are muted and struck through. The mockup's 240px label column and approximately 48px rows are desktop visual targets; narrow viewports use horizontal scrolling rather than compressing text and bars into unreadability.

**Scale and navigation:** keep Weekly / Monthly / Yearly selectable and persist the user's selected scale by the existing component mechanism. Weekly shows calendar days in the visible week, Monthly shows week bands spanning the actual month, and Yearly shows months spanning the year; column widths and date-range labels derive from the actual interval, never fixed to 42 days. Previous / next shift one week, month, or year according to scale. Today returns to the period containing the current date. Switching projects should not turn the selected scale into a hard-coded mockup default. Handle month/year rollover and leap years correctly.

**Task dates:** the backend's real `StartDate` and `DueDate` remain the only source of persisted dates. For rendering only, a Due-only task gets a three-day inclusive bar ending on Due; the UI must not present the inferred start as a saved start date. A Start-only task or a task without either date displays a dashed “Set dates” control. A fully dated task spans its start through its due inclusively, clipped to the visible period; a dated task outside the period displays a direction/date note as in the mockup. For inconsistent persisted dates (Due before Start), display a safe minimal marker instead of negative width; do not silently write corrected dates. Provide native tooltip text describing the real due date and the inferred nature of a Due-only bar. Bar, task name, and “Set dates” open the existing task drawer; saving dates there refreshes Timeline through the established data flow. Do not add bar dragging or inline date editing.

The shared task search/filter controls continue filtering Timeline rows. Remove the Timeline-only status chips and the old buckets/pill presentation. Retain Critical Path as a secondary toggle, default off, without changing the mockup-style default grid. Critical Path is an optional visual highlight layered over status colours, not a replacement for them. The empty state distinguishes no tasks / no matching tasks. Do not use the mockup's broken static “Today” reset or fixed-year suffix.

## Workload view

Render the mockup's white card with header `Team workload`, a caption `Capacity: 8 tasks per person`, and the existing Add member action. Each row has a 34px avatar; name and position; a load badge; a 10px stacked bar with the same four status colours as Timeline; `N open · N total` with an overdue count when applicable; and View tasks plus a Remove action when permitted. All project members appear, including zero-task members. A synthetic Unassigned row appears only when at least one project task has no assignees, with `Needs owner` and no Remove action. This is a task-count indicator, **not** a claim about leave, availability calendars, or working hours.

The service extends the existing Workload DTO with per-assignee status counts and overdue count; project-wide totals and existing DTO fields remain intact for current consumers. Every task assigned to multiple members contributes once to each member's row and once to the project-wide total; tasks with no assignee contribute to Unassigned only. Status segments are proportional to the fixed capacity of 8, in To Do / In Progress / Review / Done order, and the total rendered width is clamped to the track so overload does not distort layout. Numerical summary, badge, and accessible description always show the actual counts even when the visual bar is capped. Load labels use **open** tasks (all except Done): Available at 0–2, Busy at 3–4, Overloaded at 5 or more; Unassigned always displays Needs owner. Overdue means a non-Done task with DueDate before today's actual date. Workload totals always cover the entire selected project and do not change with task search/filter from the shared toolbar.

View tasks switches to the existing List tab with an assignee or Unassigned filter, rather than expanding a second private task list. Include Review tasks in the available task collection: currently the combined list omits the Review lane, which also affects Timeline assignee details. Preserve Add member's existing picker and permissions. Remove member is visible only where the current permissions allow editing and for removable members; after explicit confirmation, remove project membership **and** their assignments on all tasks in that project in a single service operation, leaving other assignees intact. Project task cards, List, and Workload then refresh; a removed member must not reappear as an assignee. Do not exercise Remove against live data in browser verification.

## Data flow and compatibility

Reuse `GET /api/projects/{id}/timeline`, `GET /api/projects/{id}/workload`, existing task APIs, and project membership endpoints. Add fields to the current Workload DTO rather than introducing a view-specific endpoint or new tables. Keep existing consumers' properties and meanings stable. Calculate status breakdown, unassigned row, and overdue with one coherent service query or bounded projection; avoid one database query per member. Membership removal and assignee removal must succeed or fail together. Do not alter permission policy. The browser date origin is the real current date; if API and browser date boundaries differ, use one explicit app date basis rather than hard-coded values.

Styles are scoped to the Projects views (existing component CSS or Projects parity layer) and use the established tokens and responsive patterns. Do not globally restyle other pages. Preserve keyboard-usable buttons, status-colour text equivalents, readable labels, and tooltip/accessible names for bars and controls. If linked CSS changes, update its cache-busting query in `index.html` without overwriting other sessions' query changes.

## Verification

Add focused service tests for per-member status breakdown (including Review and multiple assignees), overdue vs Done, zero-task members, Unassigned visibility, eight-task capacity thresholds, and membership removal with assignment cleanup / unchanged other assignees. Add UI/helper tests for scale navigation across month/year boundaries, inclusive date placement and clipping, Due-only inferred display, Start-only “Set dates”, and Review status rendering where feasible with existing test infrastructure. Run Projects tests and full solution build, reporting pre-existing failures separately. Use a real browser with live read-only project data to inspect Weekly / Monthly / Yearly navigation, Today, status legend, drawer opening, View tasks filtering, and Workload. Compare screenshots with the mockup at matching viewport, but expect content/count differences because the mockup uses fabricated sample data. Confirm no destructive action is taken against the development database.

## Explicit non-goals

No fixed six-week / 42-day timeline, no sample-data seeding, no draggable/resizable bars, no new per-member capacity settings, no availability/leave tracking, no new page or endpoint dedicated to the mockup, and no unrelated Projects redesign. The current Critical Path capability remains as a secondary visual option. Workload's search/filter independence remains intentional.
